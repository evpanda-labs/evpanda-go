evpanda-go

A passive OCPI / OCPP capture SDK that lives inside someone else's production process. It records protocol traffic, buffers it in memory, and ships it in batches — while guaranteeing it never blocks, never panics, and never grows without bound.

This document explains how the SDK is put together, what happens to a captured message between your handler and the ingestion API, and how to wire it into a service. Read Part I and Part II to understand the machine; read Part III if you just need to use it.

The design tracks evpanda-node, which is the reference implementation — same layering, same names, same wire records. Where Go diverges it is deliberate and called out, and §A lists every divergence in one place. The one substantial rewrite is the delivery loop: Node and Python poll a buffer because neither runtime can wake a sleeping worker, and Go can.

Part I

Architecture

1Constraints that shaped everything

This SDK is unusual in one respect: it runs inside a customer's charging platform, on their goroutines, in their memory, on the hot path of their revenue-carrying traffic. Nothing it does is worth a degraded charging session. Four rules follow from that, and every design decision below is downstream of them.

Invariant 1

Capture never blocks. A capture call validates, copies, and enqueues — no I/O, no channel send that can wait, no lock held across a syscall. If the upstream is down, capture cost does not change.

Invariant 2

Nothing panics into the host. Every public entry point is wrapped in a recover. Capture methods return nothing, so a fault has nowhere to surface; Flush, Close and Shutdown convert a recovered panic into an error.

Invariant 3

Memory is bounded, and the bound is a number you provision against. MaxBufferBytes is the ceiling on everything held awaiting delivery — 32 MiB by default, allocated on demand. Under stress the SDK evicts rather than accumulating.

Invariant 4

A bad config degrades, it does not crash. StartOCPI / StartOCPP always return a usable, non-nil client. A bad endpoint yields an inert client plus an error; you may log it and carry on booting.

Two consequences are worth stating plainly, because they are the trade the whole design makes. Delivery is best-effort. A batch that survives five retries and still fails is dropped, and a buffer that fills evicts its oldest entries. Losing telemetry is always preferable to slowing down a charge point. And capture is fire-and-forget: no capture method returns an error, because there is nothing a caller could usefully do with one.

2Shape of the package

One flat package, evpanda, mirroring how the Node SDK splits src/ and how Python splits evpanda/. Flat keeps the import path a caller already has (evpanda.StartOCPI, not ocpi.New(evpanda.Config{})) and avoids an internal package that exists only to dodge an import cycle.

The core knows nothing about OCPI or OCPP beyond the two structs it moves. worker.go and transport.go handle both because a message is just something that can turn itself into an ingestion record:

types.go
// message is the sealed interface the ring buffer holds, so it can carry
// either protocol without a tag.
type message interface {
	record(capturedAt string) any
}

Two methods, both dispatched off that interface, replace the type switches a previous revision used in serialize and the buffer. Adding a third protocol means adding a struct and implementing them; nothing in the core changes.

2.1  Why the adapters are their own package

The capture pipeline and the adapters change at different rates. The pipeline is done — a buffer, a goroutine, a transport, and a wire contract that only moves when the ingestion API does. Adapters accumulate framework surface indefinitely: today net/http and http.RoundTripper, tomorrow whatever a customer's CSMS is written against. Keeping them apart means the growing half cannot crowd the finished half's namespace, and go doc evpanda stays about capture.

Go's package boundary is real, though, and the split has a price. The adapters need two things the core previously kept unexported: the resolved per-body cap, so a streaming body is bounded as it is read rather than after it is buffered, and a live/inert check, so an inert or closed client costs no per-request work. Both are now one exported method.

the seam — clients.go, consumed by package ocpi
// CaptureLimits reports the resolved per-body capture cap and whether
// the client is currently capturing.
func (c *client) CaptureLimits() (maxCaptureBytes int, active bool)

The ocpi package depends on a three-method Capturer interface rather than *OCPIClient — the two capture methods plus CaptureLimits — with a compile-time assertion that the real client satisfies it. That also makes the adapters testable against a fake, with no pipeline running.

Not a leak — the documented escape hatch

Exporting CaptureLimits and RoamingIdentity.Valid is not internal plumbing escaping: they are exactly what someone writing an adapter for a framework the SDK does not ship needs. Since "call CaptureInboundMessage yourself" is the documented answer for fasthttp, gRPC gateways and the rest, the seam has to be public anyway.

The same reasoning sets where the next adapter goes. An adapter that needs a third-party import gets its own module — evpanda-go/adapters/gin with its own go.mod — because a same-module subpackage would still put gin in this module's dependency graph, and nobody should take a dependency on gin to capture OCPP traffic. Stdlib-only adapters stay in ocpi. It is the split OpenTelemetry uses for the same reason: contrib instrumentation ships as separate modules while the SDK core stays whole.

3Concurrency model

One client owns exactly one goroutine. Not a pool, not one per connection — one. It is the only thing in the SDK that performs I/O, and it is the only thing that touches the transport.

That single-goroutine rule is what makes the rest simple. Flushes are serialized because they all happen in the same place, not because a mutex says so. There is no flush lock, no in-flight promise to join, no re-entrancy guard — the loop is the guard. Producers and the worker meet at exactly one point, the ring buffer, which holds a mutex for the microseconds it takes to write a slot.

Node and Python both poll: a 200 ms timer wakes, checks a counter, and mostly goes back to sleep. That is a workaround for runtimes where a producer cannot signal a sleeping consumer. Go can, so the Go worker sleeps in a select until something actually happens — see §7. An idle SDK costs one parked goroutine and zero wakeups.

What is safe to call from where

OperationConcurrencyBlocks?

Flush is the one method that blocks, and it blocks for as long as the transport's bounded retry takes — up to a couple of minutes against a dead upstream. It is a shutdown and diagnostic tool, not something to call on a request path. Capture is already asynchronous; you do not need to flush to make it happen.

Part II

Data flow

4The pipeline, end to end

Every captured message — OCPI or OCPP, adapter or direct call — takes exactly this path. There is no second route, no fast path, no bypass.

Two things are worth noticing about where the boundary sits. First, redaction happens above it — an unredacted message is never written to the buffer, so a heap dump of a running process cannot contain a captured Authorization header. Second, the capture timestamp is stamped above it too, at chokepoint time. captured_at is when your handler saw the traffic, not when the SDK got round to shipping it, so queue delay never distorts the record.

5The chokepoint

prepareOCPI and prepareOCPP in worker.go are the single place a message is checked and transformed before it enters the queue. They are pure functions: given a message they return an envelope to enqueue, or false to drop. Keeping them pure and module-local is deliberate — it means there is one answer to "why was my message not captured?", and it can be unit-tested without a client, a server, or a goroutine.

worker.go — the OCPI chokepoint
func prepareOCPI(msg ocpiMessage, redact ocpiRedactor, maxCaptureBytes int) (bufferedMessage, dropReason) {
	if !msg.Identity.Valid() {
		return bufferedMessage{}, dropInvalidIdentity
	}
	if len(msg.Data.RequestBody) > maxCaptureBytes || len(msg.Data.ResponseBody) > maxCaptureBytes {
		return bufferedMessage{}, dropOversize
	}
	// Take ownership before redacting. From here the bytes are the SDK's,
	// so a redactor may rewrite a body in place, and the host may reuse
	// its own buffer the moment the capture call returns.
	msg.Data.own()
	return bufferedMessage{capturedAt: nowISO(), message: redact(msg)}, dropNone
}

Four things happen here, in order:

  1. Validate the identity. OCPI needs PlatformID and PlatformName; OCPP needs ChargerID. Tenant is all-or-nothing — both TenantID and TenantName, or neither. A message the SDK cannot attribute is useless downstream, so it is dropped rather than shipped as an orphan.
  2. Enforce the byte cap. An oversize body drops the whole message, never a truncated one. Half a JSON body is unparseable, and worse, truncation could slice a credentials payload in a way that defeats the redactor below.
  3. Take ownership of the bodies. The chokepoint copies every byte payload before redaction runs, so the buffered capture never aliases the host's memory. Two things follow: the host may reuse a pooled read buffer the instant the capture call returns, and a redactor may rewrite a body in place without reaching back into the caller's slice.
  4. Redact, then stamp captured_at and wrap the message in its envelope.
Why the copy is worth a memcpy per message

A capture is held until the next flush — up to FlushInterval. A body assigned straight from a reused buffer would be serialized after the host had overwritten it, so the ingestion API would receive whatever happened to be in that buffer 5 seconds later. Silent, intermittent, and indistinguishable from an SDK bug.

SetRequestBody and SetResponseBody make the transfer explicit at the call site; the chokepoint copies anyway, so the guarantee does not depend on anyone remembering them.

OCPP has one extra rule. The ingestion contract requires both direction and raw_frame when event_type is 2 (MESSAGE), so a message event missing either is dropped at the chokepoint rather than being sent and rejected with a 400.

5.1  Redaction

Redaction is a closure built once per client — defaultOCPIRedactor captures the allowlist set so it is not rebuilt per message — and applied as a pure transform. OCPI has two rules:

Header allowlist. Only listed headers survive; every unlisted header is dropped, so Authorization, Cookie and X-API-Key fall off without needing to be enumerated. OCPIAllowedHeaders extends the list and can never shrink it. The default set is deliberately small:

Credentials-token mask. The OCPI /credentials endpoint exchanges bearer tokens in the request body, where a header allowlist cannot reach. On a URL ending /credentials the token field is replaced with [redacted] — at the root for requests, under data for the response envelope. Any miss (non-credentials URL, non-JSON, no token, re-encode failure) returns the original bytes unchanged: redaction never silently drops data it could not safely rewrite.

OCPP frames are captured verbatim, so there is no OCPP redactor at all: OCPPClient.redact stays nil and the chokepoint skips the step, rather than paying an indirect call per frame to run an identity transform. The nil-able field is the seam — masking idTag in Authorize, say, arrives as a defaultOCPPRedactor plus one line in StartOCPP, with nothing in the worker or the client to change.

The other half of that contract

Because nil means "nothing to redact", a live OCPI client must never have one. StartOCPI is the only place the field is set, and the only nil-redactor client is the inert one a failed config returns — which never captures. A test pins both halves, so the invariant cannot rot silently into shipped Authorization headers.

6The buffer

A byte-bounded, drop-oldest queue. It does no I/O and knows nothing about protocols; it is a bounded handoff between many producers and one consumer.

Why bytes, not a message count

Captured messages vary by two orders of magnitude. A message count is a proxy for the thing an operator actually has to provision, and a poor one — the same 10 000 slots is 3 MiB of heartbeats or 625 MiB of capped bodies. You cannot size a container against a number that is 100× off in the common case.

Typical messageAccountedFit in 32 MiBOld: 10 000 slots
OCPP heartbeat355 B94 52010 000
OCPP meter values582 B57 65410 000
OCPI CDR push (2.4 KiB body)3 124 B10 74110 000

Byte-bounding is strictly better on both axes: the worst case drops from 625 MiB to 32 MiB, and the small messages that dominate real traffic get up to 9× more headroom. The backing slice also grows on demand, so a 50-charger deployment holds a few hundred kilobytes rather than pre-allocating for its ceiling.

Drop-oldest rather than drop-newest is a deliberate choice: during an incident the most recent frames are the ones an operator actually wants. The producer never learns that eviction happened — there is nothing useful it could do with that information, and returning an error would push a decision onto a caller who called a fire-and-forget method. The operator can act on it, though, which is what the counters in §12 are for — a different consumer at a different timescale.

Two Go-specific details make the ceiling real rather than aspirational. Eviction and drain both zero the slots they release — otherwise the backing array would pin every message the buffer ever held, since each envelope keeps a body byte slice alive. And the live region is compacted once its evicted prefix reaches half the slice, so eviction-heavy traffic cannot grow the array without bound.

Accounting charges each message its variable-length parts plus a deliberately generous fixed overhead (envelopeOverhead, 256 B) for struct fields, string and slice headers, and the slot itself. Over-counting is the safe direction: it keeps the configured budget a true ceiling. It also means the byte bound implies a message bound — 32 MiB can never hold more than ~131 000 messages however small they are — so there is no second knob to set.

enqueue returns the resulting message count. That return value is what lets the worker sleep instead of poll, which is §7.

7The worker

The whole delivery loop is one select over four channels. This is the part of the SDK that differs most from the Node reference, and it is the part worth reading the source for.

worker.go — the loop
for {
	select {
	case <-w.quit:
		return

	case <-timer.C:
		w.flush(w.ctx)
		timer.Reset(w.cfg.flushInterval)

	case <-w.wake:
		w.flush(w.ctx)
		// Restart the interval: a size-triggered flush already
		// emptied the buffer, so the pending tick would be a no-op.
		timer.Stop()
		timer.Reset(w.cfg.flushInterval)

	case ack := <-w.flushReq:
		w.flush(w.ctx)
		timer.Stop()
		timer.Reset(w.cfg.flushInterval)
		close(ack)
	}
}

7.1  The size trigger

wake is a buffered channel with exactly one slot, and producers send to it non-blocking:

worker.go — the producer side
func (w *worker) enqueue(env bufferedMessage) {
	if w.buffer.enqueue(env) < batchCap {
		return
	}
	select {
	case w.wake <- struct{}{}:
	default: // a trigger is already pending; one flush covers both
	}
}

The one-slot-plus-default pattern is what keeps Invariant 1 intact. A thousand producers arriving at once collapse into a single pending wake; none of them waits, and the worker does one flush rather than a thousand. If the worker is already mid-flush, the trigger sits in the slot and is picked up on the next turn of the loop.

7.2  Flush and drain

Flush() sends an ack channel on flushReq and waits for the worker to close it. A concurrent caller queues on the unbuffered send rather than starting a second flush — the same single-flight guarantee Node gets from sharing a promise, but achieved by the channel rather than by bookkeeping. Both the send and the wait also select on done, so a Flush racing a Close returns instead of deadlocking.

Shutdown moves the drain onto the caller's goroutine. The sequence is: close quit; wait for done (which also waits out a flush already in flight); then drain the remaining buffer in a loop until it is empty or the deadline passes. If the deadline expires while the loop is still flushing, cancelling the worker's context aborts the in-flight POST — so Close can never leave a goroutine running past its return.

worker.go — shutdown
select {
case <-w.done:
case <-ctx.Done():
	w.cancel()   // aborts the in-flight POST
	<-w.done     // the goroutine cannot outlive this call
	return ErrDrainIncomplete
}

// The loop is gone, so the drain runs here, on the caller's goroutine.
for w.buffer.length() > 0 {
	if ctx.Err() != nil {
		return ErrDrainIncomplete
	}
	w.flush(ctx)
}

8The transport

Hand-rolled over net/http. No generated client: two endpoints do not justify pulling a code-generator's transitive dependency tree into a customer's production binary.

The transport owns retry entirely. The worker calls send once and moves on; there is no retry logic anywhere else, and no caller ever sees a delivery error.

KnobValueWhy
Batch cap1000The ingestion API's maxItems; also the size-based flush trigger
Max attempts5Bounded, so a dead upstream cannot pin a goroutine indefinitely
Backoff500 ms → 30 sCapped exponential with full jitter, so restarts don't synchronize
Per-attempt timeout30 sA hung connection feeds the backoff instead of stalling the worker
Compression floor1024 BBelow this, compression costs more CPU than it saves bytes

None of these are configurable, and that is intentional. They are properties of the ingestion contract, not of a deployment, and every SDK must agree on them or the API's capacity planning stops meaning anything.

zstd holds resources. zstd.NewWriter spawns its own goroutine pool, so the transport must be closed on shutdown — worker.shutdown does it via defer, after the final drain, when no send can still be running. A client-per-tenant host would otherwise leak steadily; there is a regression test that opens and closes ten clients and counts goroutines.

9Wire contract

Both endpoints take {"messages": [ … ]} with flat, snake_case records. The SDK's internal types are deliberately not the wire types — record(capturedAt) maps between them — so the ergonomic Go shape and the ingestion shape can evolve independently.

POST /v1/ocpi — one record
{

  "platform_id":          "acme",
  "platform_name":        "Acme Mobility",

  "tenant_name":          null,
  "direction":            "IN",
  "http_method":          "POST",
  "url":                  "/ocpi/2.2/cdrs",
  "response_status_code": 201,
  "request_headers":      { "content-type": "application/json" },
  "request_body":         "eyJpZCI6ImNkci0xIn0=",
  "response_headers":     { "content-type": "application/json" },
  "response_body":        null
}
POST /v1/ocpp — one record
{
  "charger_id":    "CP-001",
  "connection_id": "5f2c…",          // SDK-minted, stable per socket
  "tenant_id":     null,
  "tenant_name":   null,
  "captured_at":   "2026-08-27T09:14:22.418Z",
  "event_type":    2,                // 0 DISCONNECT · 1 CONNECT · 2 MESSAGE
  "direction":     "FROM_CP",        // required iff event_type == 2
  "raw_frame":     "WzIsImlkIiwiQm9vdE5vdGlmaWNhdGlvbiIse31d"
}

Three conventions matter, and all three are shared with the Node SDK:

  • Absent means null, never a zero value. Optional fields are Go pointers or json.RawMessage without omitempty. A missing status code must serialize as null, not 0 — the difference between "no response" and "status zero" is real, and a dropped key would make it invisible.
  • Bodies are base64, always. Both OCPI HTTP bodies and OCPP wire frames. The ingest server decodes before persistence, so downstream consumers see plain UTF-8; encoding keeps the contract uniform across protocols and binary-safe for whatever comes next (ISO 15118 EXI, OCPP 2.0.1 security extensions).
  • Timestamps are RFC 3339, UTC, millisecond precision — layout 2006-01-02T15:04:05.000Z07:00 after .UTC(). The server normalizes anyway; matching it exactly keeps round-trip tests meaningful.

11Lifecycle

the whole lifecycle surface
panda, err := evpanda.StartOCPI(cfg)   // never nil, even on error
if err != nil {
	log.Printf("evpanda: %v (running inert)", err)
}

err = panda.Flush()                    // deliver now, wait for it
err = panda.Close()                    // drain within DrainTimeout
err = panda.Shutdown(ctx)              // drain against your own deadline

An inert client is a real client. When Start* fails it returns a client with no worker. Every capture method is a no-op, Flush and Close return nil, Connection still hands back a usable session, and the adapters return your handler and transport unwrapped. This is why the constructor returns (*Client, error) rather than failing hard: a telemetry SDK must never be the reason a charging platform won't boot.

Close is idempotent, and post-close captures are safe. The client detaches its worker under a lock, so the second Close sees nil and returns nil. A capture that arrives after close finds no worker and returns. Both are ordinary, expected paths — not error conditions.

Errors mean drain, not delivery. Close and Shutdown return ErrDrainIncomplete when the deadline expired with messages still buffered — meaning some telemetry was dropped on the way out. They do not report delivery failures, which are retried and dropped by design. If you want visibility into those, set Debug: true and each dropped batch is logged with its reason.

typical shutdown
ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()

srv.Shutdown(ctx)                      // stop accepting first…
if err := panda.Shutdown(ctx); err != nil {
	log.Printf("evpanda: %v", err)     // …then drain what was captured
}

Order matters: drain the SDK after the server stops accepting, or you will be draining a buffer that is still filling.

12Knowing whether it's working

The SDK discards data in five places by design. Four of them were invisible, which made the single most likely integration bug — an adapter mounted before the host's auth layer — look exactly like a working SDK on an idle system. No error, no log, no signal, and a support ticket that could not be answered.

12.1  Counters

Stats() is always available: no log mode turns it off, and it is safe on an inert or closed client (a closed one reports its final totals). The counters live on the client rather than the worker precisely so the lifetime tally survives Close.

CounterWhat a high value means
Captured = 0The capture path is not wired in
DroppedInvalidIdentity resolution failing — usually an adapter mounted before auth
DroppedOversizeBodies exceed MaxCaptureBytes
DroppedEvictedUpstream can't keep up, or MaxBufferBytes is too small
DroppedUndeliverableNetwork, API key, or ingestion fault
DroppedPanicA bug in the SDK

One counter per root cause is the whole design goal: it turns an open-ended investigation into a lookup, in production, with no redeploy. It is a pull-based snapshot rather than an emitter, so it composes with Prometheus or OTel without the SDK depending on either.

12.2  Logging is on by default, and rate-bounded

The policy, and the hazard it avoids

A silent SDK that captures nothing is indistinguishable from a working one, so the default is not silence — problems are reported without the host switching anything on.

What makes that safe is that the SDK logs the rate, not the event. The adapter-before-auth fault drops on every request; per-event logging would emit at request rate, flood the host's log pipeline, and cost them real money in ingestion fees. Instead: one summary line per minute, carrying everything that happened in the window.

LogModeWhat you get
LogModeSilentNothing, ever. Counters still work.
LogModeErrorsDefault. Config problems at startup, plus the once-a-minute summary when captures are dropping.
LogModeDebugAdds per-batch delivery failures, recovered capture faults, and a close summary even on a clean run.

Leaving LogMode unset consults $EVPANDA_LOG, which is the point: an operator can silence the SDK mid-incident with a restart rather than a code change. An explicit field wins over the environment — matching how APIKey resolves — and since most hosts never set the field, the env var still reaches almost every deployment. Anything unrecognised in either falls back to errors; a typo must not be able to silence the SDK, which is the same rule the tunables follow in §10.

The health line rides the worker's existing select, so reporting costs no extra goroutine and can never overlap a flush. It reports the delta since the last line, so a fault that stops recurring stops being logged.

13OCPP

OCPP identity is known at connect time — you authenticated the charge point during the handshake — so there is no resolver. The recommended path is a session handle: it mints the connection ID, records the connect, and carries the identity, so per-frame calls carry neither.

a CSMS WebSocket handler
panda, err := evpanda.StartOCPP(evpanda.OCPPConfig{
	BaseConfig: evpanda.BaseConfig{Endpoint: "https://ingest.evpanda.io"},
})
if err != nil {
	log.Printf("evpanda: %v (running inert)", err)
}
defer func() { _ = panda.Close() }()

http.HandleFunc("/ocpp", func(w http.ResponseWriter, r *http.Request) {
	// Your own charge-point identification — whatever your CSMS already
	// does at handshake time: parse the path, read Basic auth, check a
	// client certificate, hit your DB.
	identity, ok := resolveChargerIdentity(r)
	if !ok {
		http.Error(w, "unknown charge point", http.StatusUnauthorized)
		return
	}

	conn := upgrade(w, r)
	sess := panda.Connection(identity)   // records the connect
	defer sess.Disconnect()              // records the close

	for {
		frame, err := conn.Read()
		if err != nil {
			return
		}
		sess.Message(frame, evpanda.FromCP)

		reply := handleFrame(frame)      // your CSMS logic
		conn.Write(reply)
		sess.Message(reply, evpanda.ToCP)
	}
})

CaptureConnect, CaptureMessage and CaptureDisconnect are the flat primitives underneath, each taking an OCPPMessageInput. Use them where a session handle does not fit — a connection whose lifetime you do not own, or replaying frames from a log.

14OCPI, directly

OCPI traffic flows both ways between roaming partners, and the SDK records each direction separately. The method name sets the direction — there is no direction field to pass, and no way to get it backwards.

MethodYou are the…Typical case
CaptureInboundMessage server An eMSP pushes a CDR or session update to your endpoints
CaptureOutboundMessage client You pull a partner's locations, or post a token authorization
Easy to get wrong

Identity is always the partner on the other side of the exchange — never your own platform. Inbound and outbound both. A record attributed to yourself is not wrong at the API, it is just useless.

direct capture
identity := evpanda.RoamingIdentity{PlatformID: "acme", PlatformName: "Acme Mobility"}

panda.CaptureInboundMessage(evpanda.OCPIMessageInput{
	Identity: identity,
	Data: evpanda.HTTPExchange{
		Method:          "POST",
		URL:             "/ocpi/2.2/cdrs",
		StatusCode:      201,
		RequestHeaders:  map[string]string{"content-type": "application/json"},
		ResponseHeaders: map[string]string{"content-type": "application/json"},
		RequestBody:     []byte(`{"id":"cdr-1"}`),
		ResponseBody:    []byte(`{"status_code":1000}`),
	},
})

StatusCode and both bodies are optional; header maps may be nil. Use this path when you have identity in hand and the adapters do not fit — a framework the middleware cannot wrap, or a replay from an audit log.

15OCPI adapters

The adapters do the assembly for you: collect headers and bodies, resolve identity, call the right method. Both are stdlib shapes, so neither pulls a framework dependency.

inbound — net/http middleware
func auth(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		partner, ok := lookupPartner(r.Header.Get("Authorization"))
		if !ok {
			http.Error(w, "unknown partner", http.StatusUnauthorized)
			return
		}
		ctx := ocpi.ContextWithIdentity(r.Context(), evpanda.RoamingIdentity{
			PlatformID:   partner.ID,
			PlatformName: partner.Name,
		})
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}

mux := http.NewServeMux()
mux.Handle("POST /ocpi/2.2/cdrs", cdrHandler)

srv := &http.Server{Handler: auth(ocpi.Middleware(panda)(mux))}

func(http.Handler) http.Handler is the stdlib middleware shape, so it drops into net/http, chi, gorilla/mux, echo.WrapMiddleware and gin.WrapH unchanged.

The request body is recorded as your handler reads it, via a capped tee on r.Body — a handler that ignores the body records none, and a streaming handler is never forced into memory. This differs from Node, which reads req.body after a body parser has already run; Go middleware executes before the handler, so teeing is the only option that does not consume the stream. The response is teed on its way out through a responseRecorder that implements Unwrap, Flush and Hijack, so http.ResponseController and direct type assertions both still reach the real writer. A hijacked connection is marked and skipped: after an upgrade there is no HTTP response left to describe.

outbound — http.RoundTripper
client := &http.Client{Transport: ocpi.RoundTripper(panda, nil)}  // nil ⇒ DefaultTransport

// You already looked the partner up to get their Token B —
// stamp identity on the same context.
ctx = ocpi.ContextWithIdentity(ctx, evpanda.RoamingIdentity{
	PlatformID:   partner.ID,
	PlatformName: partner.Name,
})
req, _ := http.NewRequestWithContext(ctx, http.MethodPost,
	partner.BaseURL+"/ocpi/2.2/sessions", body)
req.Header.Set("Authorization", "Token "+partner.TokenB)

resp, err := client.Do(req)

Because it is an http.RoundTripper, it captures anything that goes through that client — including a generated OCPI client, as long as it accepts an *http.Client.

The adapter never mutates the request you handed it (the RoundTripper contract requires this — it clones first) and never alters the response. The one change it makes is stripping the X-EVPanda-* headers from the outgoing copy, so a partner never receives them and your TenantID / TenantName stay internal. Stripping happens even on a closed client, so closing mid-flight cannot start leaking them. A transport error propagates unchanged and captures nothing — there was no exchange to record.

16Identity resolution

Both adapters resolve identity the same way, and the order is the point.

ocpi/adapter.go — the context helpers
func ContextWithIdentity(ctx context.Context, id RoamingIdentity) context.Context
func IdentityFromContext(ctx context.Context) (RoamingIdentity, bool)

The context path is preferred for three reasons: it is typed, so a misspelling is a compile error rather than a silently uncaptured request; it cannot leak onto the wire, because there is nothing to strip; and it survives any header rewriting between your auth layer and the adapter. The key is an unexported struct type, so nothing outside the package can collide with or overwrite the value.

The header path exists for hosts whose identity is already stamped by an upstream proxy or a different process. Four headers, matched case-insensitively, exported as constants:

ConstantHeaderField
ocpi.HeaderPlatformIDX-EVPanda-Platform-IdPlatformID — required
HeaderPlatformNameX-EVPanda-Platform-NamePlatformName — required
HeaderTenantIDX-EVPanda-Tenant-IdTenantID — optional
HeaderTenantNameX-EVPanda-Tenant-NameTenantName — optional

15.1  Custom resolvers

If identity lives somewhere neither the context nor the headers reach — a client certificate, a path prefix, your own session store — replace the shipped resolver:

a path-prefix resolver
byPath := func(r *http.Request) (evpanda.RoamingIdentity, bool) {
	name, ok := strings.CutPrefix(r.URL.Path, "/partners/")
	if !ok {
		return evpanda.RoamingIdentity{}, false   // not captured
	}
	return evpanda.RoamingIdentity{PlatformID: name, PlatformName: name}, true
}

ocpi.Middleware(panda, ocpi.WithResolver(byPath))
ocpi.RoundTripper(panda, nil, ocpi.WithResolver(byPath))

The resolver takes the whole *http.Request rather than Node's synthetic {method, url, requestHeaders} context — in Go the request already carries all of it, including the context. A resolver that panics is treated as "no identity"; the request is served normally either way.

Appendix

Notes on the port

ACross-SDK parity

Layering, naming and wire records track evpanda-node exactly. These are the places Go deliberately differs, and why.

ConcernNodeGo
Delivery loop 200 ms poll of a counter select on four channels; no polling (§7)
Flush serialization Shared in-flight promise Single goroutine — structural, no lock
Constructor failure start() swallows, returns inert (*Client, error) — inert and the reason
Shutdown deadline close(deadlineMs?) Close() uses DrainTimeout; Shutdown(ctx) takes yours
Adapter bridge _internal field, stripped from typings Adapters are a subpackage over a 3-method Capturer seam
Inbound adapter express/connect; reads req.body net/http middleware; capped tee on r.Body
Outbound adapter Two: fetch and axios One: http.RoundTripper covers both roles
Identity carrier Headers only context.Context first, headers second (§16)
Message dispatch Type predicate in serialize record() method on a sealed interface
Buffer bound bufferCapacity — message count MaxBufferBytes — bytes (§6)
Logging default debug: false ⇒ completely silent LogMode ⇒ rate-bounded errors on (§12)
Drop visibility None Stats() counters, one per root cause

The context.Context path has no Node equivalent because there is nothing to have one — JS has no request-scoped value carrier that survives a middleware chain the way Go's does. It is the one genuinely new capability in the Go port, rather than a translation.

The last three rows are policy changes, not language differences, and the reasoning behind each applies to Node and Python unchanged: a message count is an untranslatable memory bound in any runtime, and a silent SDK is indistinguishable from an idle one in any language. Until those SDKs follow, the three differ in observable behaviour — which is worth knowing when a customer runs more than one.

BKnown gaps and open questions

Recorded so they are decisions rather than oversights.

Fixed in the last scan

The delivery goroutine had no panic recovery. Invariant 2 covered the capture path, but the SDK's own goroutine was bare — a fault there would have taken the host's process down, which is precisely what the SDK exists not to do. It now recovers, counts the loss, and logs at Error level; delivery stops rather than the host.

nextDelay overflowed. backoffBase<<attempt goes negative past attempt 34 and rand.Int64N panics on that — on the worker goroutine, so it would have hit the bug above. Unreachable at backoffMaxAttempts of 5, and a landmine for whoever raises it. The shift is guarded now.

Spec disagreement

response_status_code is in the ingestion spec's required list but is not marked nullable — yet both Node and Go send null when the status is absent. If Atlas validates strictly, an OCPI capture without a status code will be rejected with a 400. Go matches Node here because Node is the reference, but the spec and both SDKs disagree and one of them should move.

  • OCPP redaction is a seam, not a feature. Frames are captured verbatim today. idTag in Authorize is the obvious first candidate.
  • OCPIMessage / OCPPMessage stay unexported. Node and Python export them, but only as type-only exports; in Go they would be public structs nobody constructs. Exporting them is a one-line change if parity turns out to matter.
  • The counters stay inside the process. §12 makes drops visible to whoever runs the host — but EVPanda's own ingestion API still cannot tell a broken integration from an idle one. Piggybacking the counters onto the ingest request (as a header; counts, not content) would let the dashboard flag a customer whose identity resolution is failing without them lifting a finger, turning support from reactive to proactive. It needs an ingestion contract change, so it is a follow-on — but it is where the counters are heading, and it is why they are shaped as a snapshot.
  • The sink is hard-wired to the ingestion API. worker.flush calls transport.send directly. Narrowing that to a one-method interface — take a batch, deliver or drop, never error — would make "ship to a local collector instead of the cloud" a config change rather than a rewrite, which is the door to the agent model if a large operator ever wants SDK upgrades decoupled from CSMS deploys. Cheap to do now while there are no callers; expensive once there are.
  • One client per protocol per process is assumed. Running many (per tenant, say) works and is leak-tested, but each carries its own goroutine, ring and zstd encoder pool — the memory bound multiplies.
